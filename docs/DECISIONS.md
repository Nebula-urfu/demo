# DECISIONS: решения там, где в документах и макете нет ответа

| № | Решение | Причина |
|---|---|---|
| 1 | Версии (проверены `npm view` 24.10.2026): Node 26.12.0 (Nuxt требует `^22.22.3 \|\| ^24.15.0 \|\| >=26`), Nuxt 4.6.2 (Nitro 2.13.5, Vite 8), Tailwind 4.3.3 + `@tailwindcss/vite`, `better-sqlite3` 13.0.3 (собранный бинарник есть, `node:sqlite` не понадобился), Vitest 5.0.5, TypeScript 5.9.3 (не 7: `vue-tsc` 3.3 рассчитан на 5.x), vue-tsc 3.3.13 | Выяснено на фазе 0 |
| 2 | Бизнес-логика лежит в `server/domain/`, а не в `server/modules/` из `CLAUDE.md` | Nitro 2.13 считает `server/modules/*` своими модулями и загружает каждый файл при сборке (падает на импорте БД) |
| 3 | `ssr: false` (SPA), корень приложения `app/` (Nuxt 4) | Токен в cookie и данные только через `/api/v1`: серверный рендер не нужен, меньше расхождений |
| 4 | `npm install` на npm 12 блокирует скрипты установки. В `package.json` добавлено `allowScripts` для `better-sqlite3` и `esbuild` | Чтобы `npm install` и `npm run dev` работали без ручных шагов |
| 5 | `schema.sql` читается при старте из server assets (`nitro.serverAssets`, плагин `00-db.ts`); тесты передают её через `setSchema()` | Nitro 2 не умеет `?raw`-импорт |
| 6 | Адрес и порт `127.0.0.1:3000` заданы в `nuxt.config.ts` (`devServer`), флаг `--host` не обязателен | Сайт принимает любой вход |
| 7 | В ответ `GET /package` и в `PackageDocument` добавлено поле `version` (в схеме `ProcurementPackage` его нет) | Без него клиент не знает версию для `submitPackage` (сценарий DEMO, шаги 23–26). Схема не запрещает лишних полей, контракт не менялся |
| 8 | `GET /dev/contractors` и `GET /dev/events` возвращают `{items: [...]}` | В API.md формат не задан |
| 9 | Метод НМЦ кроме `average_of_quotes` даёт `400`. Новая версия расчёта наследует `lastReviewComment` предыдущей | Метод один; комментарий остаётся виден сотруднику после пересчёта |
| 10 | Новая версия ТЗ после правки сотрудника и новая версия пакета наследуют `lastReviewComment` предыдущей версии | Сотрудник видит последний комментарий проверяющего, пока работает |
| 11 | `deleteQuote`: если остались КП и шаг был `PROCESSING`, а извлекаемых больше нет, шаг становится `DRAFT_READY` | Иначе шаг навсегда в `PROCESSING` |
| 12 | Фото в форме заявки обязательно: «Добавьте хотя бы одно фото проблемы» (состояние «Нет фото» в макете и `minItems: 1` в контракте) | В SCREENS.md фото «необязательно», макет и контракт главнее |
| 13 | Ответ `500` содержит `code: VALIDATION_ERROR`, так как в перечислении `Problem.code` нет кода внутренней ошибки | Контракт не менять |
| 14 | Курсор пагинации это строка со смещением, `nextCursor = null` на последней странице. `listRequests` и `listApprovals` в интерфейсе запрашивают `limit=100` | По API.md |
| 15 | Из экрана «Новая заявка» не перенесены «Насколько срочно», «Сохранить черновик» и редактируемый адрес | В `RequestCreate` нет таких полей, адрес берётся из сессии (SCREENS.md) |
| 16 | Экраны макета без операций в API и без записи в SCREENS.md не сделаны: Главная, Профиль, Уведомления, Шаблоны документов, Библиотека договоров, Подрядчики, Карточка подрядчика, «Откуда эта цифра», Распознавание КП, тёмная тема. Пункты навигации «Справочники» и «Уведомления» не выводятся | Правило «не придумывать экраны и поля», PROMPT запрещает тёмную тему |
| 17 | Экран входа в макете убран («вход будет через внешний сервис»). `/login` сделан по SCREENS.md из компонентов макета. Переключатель роли в шапке выполняет вход под выбранной ролью | Нужен для демо |
| 18 | Фрейм «24 Журнал согласований» не удалось получить (лимит вызовов Figma MCP на тарифе Starter). Журнал сделан по образцу таблицы «Входящие» и заметке «Для фронтенда»: фильтр над таблицей, шапка таблицы закреплена, на телефоне карточки | Нет данных |
| 19 | Фрейм «13 Конкурсная документация», «15 Договор», «22/23 Проверка НМЦ и пакета» по скриншотам не смотрел (лимит MCP). Вёрстка по общим правилам макета и заметкам «Для фронтенда» | То же |
| 20 | Логотип YKit набран шрифтом Unbounded (векторов макета не получено), большой знак Y в синих блоках нарисован inline SVG приблизительно | Нет данных |
| 21 | Номер заявки «№1042» в макете заменён первыми 6 символами UUID: числового номера в API нет | Нет данных |
| 22 | Цвета ошибок и сбоя ИИ (`danger-ink` #b42318, `danger-tint` #fde8e6) не из токенов макета, нужны для `NEEDS_REWORK` и `AI_FAILED` | В макете такого состояния нет |
| 23 | Шаги на экране сотрудника: `QUOTES_NMC` в `NOT_STARTED` доступен, если ТЗ утверждено (иначе его не открыть и не начать). Остальные не начатые шаги неактивны. Открытый при входе шаг не переключается сам | Удобство демо |
| 24 | «Отправить на проверку» для ТЗ доступно только в `DRAFT_READY` (так в API.md), не в `NEEDS_REWORK` из SCREENS.md; для ТЗ состояния `NEEDS_REWORK` не бывает | API.md главнее |
| 25 | В таблице победителя колонка «Сумма баллов» это сумма трёх баллов ИИ (в макете веса 60/20/20, в API их нет). «Изменить веса» и «Сформировать протокол» не сделаны | Нет данных |
| 26 | Страница сотрудника опрашивает заявку раз в секунду, пока есть шаг `PROCESSING`, иначе раз в 3 секунды (иначе решение проверяющего не появится без перезагрузки) | Удобство демо |
| 27 | Если жителю виден только `RequestStatus`, «Ход заявки» показывает три пункта (принята, в работе, выполнена). Блоки «Комментарий для УК» и «Оставить отзыв» не сделаны | Нет API |
| 28 | «Скачать всё» отдаёт один zip: `GET /api/v1/dev/package/{requestId}/zip[?version=N]` (STAFF, REVIEWER), архив собирает сервер (`server/utils/zip.ts`, без зависимостей, внутри текстовые заглушки документов). Кнопка есть у сотрудника на шаге «Пакет» и у проверяющего на экране проверки пакета | Просьба пользователя |
| 29 | Фото заявки теперь хранятся: клиент отправляет файл в `POST /dev/files` как multipart, сервер кладёт изображения до 5 МБ в `mock_files.content`, `GET /dev/files/{id}/download` отдаёт их как есть (остальные файлы по-прежнему заглушка). Это меняет SPEC, п. 9. Фото показываются галереей (карточка жителя, триаж), превью при выборе и миниатюра в списке жителя; картинки грузятся с токеном и показываются через blob-URL | Просьба пользователя |
| 30 | В `RequestSummary` добавлено поле `photoId` (первое фото) для миниатюры в списке; схема лишних полей не запрещает | Иначе для миниатюры нужен запрос на каждую заявку |
