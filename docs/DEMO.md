# DEMO: сценарий демонстрации

Сценарий проходит от подачи заявки жителем до `COMPLETED`. По нему пишется `scripts/demo.sh` (bash, требует `curl` и `jq`) и тест `tests/smoke.test.ts`. Команды в этом документе работают в **fish**.

## Запуск

```fish
env DEMO_AI_DELAY_MS=0 npm run dev -- --host 127.0.0.1
```

Сайт и API слушают `127.0.0.1:3000`. Мок ИИ всё равно работает асинхронно (результат появляется через долю секунды), поэтому в сценарии нужен опрос состояния.

## Вход (любые данные)

```fish
set resident (curl -s -X POST 127.0.0.1:3000/api/v1/dev/login -H 'Content-Type: application/json' -d '{"username":"anna"}' | jq -r .token)
set staff    (curl -s -X POST 127.0.0.1:3000/api/v1/dev/login -H 'Content-Type: application/json' -d '{"username":"staff-ivan"}' | jq -r .token)
set reviewer (curl -s -X POST 127.0.0.1:3000/api/v1/dev/login -H 'Content-Type: application/json' -d '{"role":"REVIEWER"}' | jq -r .token)
```

Во всех `curl` с телом нужен заголовок `Content-Type: application/json`. Вход принимает любое тело, в том числе пустое или не JSON: тогда получится гость с ролью `RESIDENT`. Сценарий в `demo.sh` входит под тремя ролями явно.

## Шаги сценария

В скобках: ожидаемый результат. `опрос` значит повторять `GET` до нужного состояния, не дольше 15 секунд.

| № | Кто | Действие | Ожидание |
|---|---|---|---|
| 1 | всё | `POST /dev/reset`, затем три входа (житель, сотрудник, проверяющий) | Три токена |
| 2 | житель | `POST /dev/files`, затем `POST /requests` с описанием «Протечка кровли над подъездом» и `Idempotency-Key` | `201`, статус `ACCEPTED` |
| 3 | житель | Повторный `POST /requests` с тем же ключом | Та же заявка, `id` не изменился |
| 4 | сотрудник | `GET /requests` | Заявка в списке |
| 5 | сотрудник | `GET /requests/{id}`, опрос до `steps[TRIAGE] = DRAFT_READY` | Статус `IN_PROGRESS` |
| 6 | сотрудник | `GET /requests/{id}/triage`, `POST /triage/confirm` с предложением | Шаг `TRIAGE` в `APPROVED` |
| 7 | сотрудник | `GET /tz`, `PUT /tz` с ответами на два вопроса и правкой секции | Версия 2, `origin = STAFF` |
| 8 | сотрудник | `PUT /tz` со старой `baseVersion` | `409 STALE_VERSION` |
| 9 | сотрудник | `POST /tz/submit` | `201`, `Approval` в `PENDING` |
| 10 | проверяющий | `GET /approvals`, `GET /approvals/{id}`, `POST /reject` без комментария | `400` |
| 11 | проверяющий | `POST /reject` с комментарием | Шаг `TZ` в `PROCESSING` |
| 12 | сотрудник | Опрос `GET /tz` до версии 3 (`origin = AI`, есть `lastReviewComment`) | Шаг `TZ` в `DRAFT_READY` |
| 13 | сотрудник | `POST /tz/submit` с версией 3 | Новая задача проверки |
| 14 | проверяющий | `POST /approve` | Шаг `TZ` в `APPROVED` |

| 21 | сотрудник | Опрос `GET /tender` до `DRAFT_READY` | Есть `winnerProposal` и два документа |
| 22 | сотрудник | `PUT /tender/winner` с КП, предложенным ИИ | Договор `STANDARD` (КП 1) |
| 23 | сотрудник | `GET /package`, `POST /package/submit` | Четыре документа, `Approval` `PACKAGE` |
| 24 | проверяющий | `POST /reject` с комментарием | `PACKAGE` и `TENDER` в `NEEDS_REWORK` |
| 25 | сотрудник | `PUT /tender/winner` с КП 3 | Договор `NON_STANDARD`, есть `lawyerNotes`, пакет версии 2 |
| 26 | сотрудник | `POST /package/submit` с версией 2 | Новая задача проверки |
| 27 | проверяющий | `POST /approve` | `PACKAGE` в `APPROVED`, заявка `COMPLETED` |
| 28 | житель | `GET /requests/{id}` | Статус `COMPLETED`, нет полей `steps` и `author` |
| 29 | проверяющий | `GET /approval-journal` | Пять записей: отказ и утверждение ТЗ, утверждение НМЦ, отказ и утверждение пакета |
| 30 | любой | `GET /dev/events` | События `ai.jobs`, `ai.results`, `notifications` |

## Проверки ошибок (в конце сценария)

| Проверка | Ожидание |
|---|---|
| `GET /requests` без токена | `401` |
| Житель вызывает `POST /approvals/{id}/approve` | `403` |
| Сотрудник другой организации (вход с `orgId = other-org`) вызывает `GET /requests/{id}` | `404` |
| Другой житель того же УК вызывает `GET /requests/{id}` | `404` |
| Сотрудник вызывает `POST /tz/submit` повторно (шаг уже `IN_REVIEW` или `APPROVED`) | `409 STEP_NOT_ALLOWED` |
| `POST /requests` без `Idempotency-Key` | `400` |
| Попытка изменить или удалить запись `approval_journal` напрямую в SQLite | Ошибка `approval_journal is append-only` (проверяется тестом) |

## Сбой ИИ (отдельный мини-сценарий)

1. Житель подаёт заявку с описанием «Течёт крыша [fail]».
2. Опрос до `TRIAGE = AI_FAILED` и `TZ = AI_FAILED`.
3. Сотрудник вызывает `POST /steps/TRIAGE/restart` (`202`), опрос до `DRAFT_READY`.

## Аварийная заявка (отдельный мини-сценарий)

1. Житель подаёт заявку «Прорыв трубы, затопило подъезд».
2. Триаж предлагает `EMERGENCY` и `EMERGENCY_CONTRACTOR_CALL`.
3. В `GET /dev/events` уведомление STAFF с `urgent = true`.
4. В `GET /requests` у сотрудника эта заявка выше остальных.

## Итог

В конце `demo.sh` печатает `DEMO OK`, если все ожидания выполнены, иначе завершается с ненулевым кодом и сообщает, какой шаг не прошёл.

## Показ в интерфейсе (5 минут)

Откройте `http://127.0.0.1:3000` в двух окнах браузера (или обычное и приватное), чтобы быть жителем и сотрудником одновременно. Третья роль, проверяющий, входит в обычном окне после выхода.

1. Окно 1: «Войти как житель», «Подать заявку», описание «Протечка кровли над подъездом», подъезд, фото. Показать статус «Принята».
2. Окно 2: «Войти как сотрудник», открыть заявку. Показать ожидание ИИ и появление черновика триажа и ТЗ. Подтвердить триаж.
3. Править ТЗ, ответить на вопросы, «Отправить на проверку».
4. Выйти, «Войти как проверяющий», в очереди открыть задачу, «Вернуть на доработку» с комментарием, затем у сотрудника показать новый черновик с комментарием, снова отправить и утвердить.
5. Сотрудник: письмо запроса КП, три КП, сравнение (подсвеченные расхождения), расчёт НМЦ, отправка. Проверяющий утверждает.
6. Сотрудник: конкурс, победитель, пакет, отправка. Проверяющий утверждает. Заявка `COMPLETED` (у жителя тоже).
7. «Демо-панель»: журнал событий с заданиями ИИ и уведомлениями. Журнал согласований у проверяющего.
