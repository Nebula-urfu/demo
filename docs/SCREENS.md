# SCREENS: экраны и поведение по ролям

Этот документ описывает **что должно быть на экранах и какие вызовы API они делают**, но не внешний вид. Внешний вид, расположение и тексты кнопок берутся из макета (`docs/DESIGN.md`). Если в макете для экрана есть фрейм, он главнее; если фрейма нет, делай простейший экран из компонентов макета и запиши в `docs/DECISIONS.md`.

Операции названы по `operationId` контракта, подробности поведения в `docs/API.md`.

## Общее

- Баннер «Демо: данные вымышленные» виден на каждой странице.
- Токен в cookie `demo_token`, профиль (роль, имя, организация) в `useSession`. Нет токена или ответ `401`: переход на `/login`.
- Навигация зависит от роли. Страница чужой роли открывается как `403`-экран «Недоступно для вашей роли».
- Ошибки `problem+json` показываются понятным текстом (`title`, `detail`). `409 STALE_VERSION` предлагает обновить страницу, `409 STEP_NOT_ALLOWED` показывает «Действие сейчас недоступно».
- Пока шаг в `PROCESSING`, страница каждую секунду перезапрашивает свои данные и показывает индикатор ожидания. Для `AI_FAILED` показывается ошибка и (сотруднику) кнопка «Повторить» (`restartAiStep`).
- Состояния шагов и заявки показываются **одним общим компонентом статуса** (7 состояний `StepState`, 3 статуса `RequestStatus`), внешний вид из макета.
- Во всех мок-текстах видна пометка «ДЕМО».
- **Скачивание файлов.** Эндпоинту `GET /dev/files/{fileId}/download` нужен заголовок `Authorization`, а обычная ссылка `<a href>` его не отправит. Кнопка «Скачать» загружает файл через `$fetch` с токеном (ответ как `blob`) и сохраняет его под именем документа.

## Маршруты

| Маршрут | Роли | Назначение |
|---|---|---|
| `/login` | все | Вход |
| `/requests` | RESIDENT, STAFF | Список заявок |
| `/requests/new` | RESIDENT | Подача заявки |
| `/requests/[id]` | RESIDENT, STAFF | Карточка заявки |
| `/approvals` | REVIEWER | Очередь проверки |
| `/approvals/[id]` | REVIEWER | Проверка и решение |
| `/journal` | REVIEWER | Журнал согласований |
| `/dev` | все | Журнал событий и сброс (служебный экран) |

После входа: RESIDENT и STAFF на `/requests`, REVIEWER на `/approvals`.

## `/login`

Поля: имя, пароль, роль (необязательный выбор: житель, сотрудник, проверяющий), организация и адрес (необязательно, можно свернуть в «Дополнительно»). Любые значения принимаются, включая пустые. Кнопка «Войти» вызывает `POST /api/v1/dev/login`. Подсказка на экране: «Демо: подойдёт любой логин и пароль».

Три кнопки быстрого входа «Войти как житель / сотрудник / проверяющий» вызывают тот же эндпоинт с заранее заданной ролью. Нужны, чтобы показывать демо без набора текста.

## `/requests` (список)

- Вызов: `listRequests`. Показывает адрес, подъезд, описание (обрезано), срочность, статус заявки, текущий шаг и его состояние, время.
- **RESIDENT**: только свои заявки. Кнопка «Подать заявку» ведёт на `/requests/new`. Поля `urgency`, `currentStep` ему не приходят (см. `docs/API.md`, `getRequest`), показываются только статус и описание.
- **STAFF**: заявки организации, срочные выше остальных (порядок задаёт сервер). Фильтр по статусу на клиенте. Срочные помечены.
- Пустой список: пустое состояние с подсказкой.

## `/requests/new` (RESIDENT)

Поля: описание (обязательно), подъезд (обязательно), фото (выбор файлов, необязательно). Адрес показывается из сессии только для чтения.

- Фото: для каждого выбранного файла вызывается `POST /api/v1/dev/files` с `name`, `mediaType`, `sizeBytes` файла, содержимое не читается. Полученные `fileId` идут в `photoFileIds`.
- Отправка: `createRequest` с `Idempotency-Key` (случайный UUID, генерируется при открытии формы и не меняется при повторной отправке). Двойной клик не создаёт две заявки.
- Успех: переход на `/requests/[id]` с сообщением «Заявка принята».

## `/requests/[id]` (карточка)

Вызов: `getRequest`. Для STAFF первый вызов переводит заявку из `ACCEPTED` в `IN_PROGRESS` (серверное поведение).

### RESIDENT

Только статус заявки, описание, адрес, подъезд, фото (имена), даты. Шагов, срочности и подробностей закупки он не видит. Вспомогательный текст берётся из макета. Если в макете его нет, показывается только статус заявки.

### STAFF: рабочее место

Верхняя часть: адрес, срочность, статус, пять шагов по порядку (`TRIAGE`, `TZ`, `QUOTES_NMC`, `TENDER`, `PACKAGE`) с состояниями. Ниже панель текущего шага. Шаги, которые ещё не начаты, показываются неактивными. Любой уже начатый шаг можно открыть для просмотра.

**Шаг TRIAGE** (`getTriage`, `confirmTriage`)
- Показывает предложение ИИ: срочность, вид работ, маршрут. Поля можно изменить (срочность выбором, вид работ текстом, маршрут выбором из двух значений).
- Кнопка «Подтвердить» (`confirmTriage`) доступна в `DRAFT_READY`. После подтверждения показывается кто и когда подтвердил.
- `AI_FAILED`: сообщение и «Повторить».

**Шаг TZ** (`getTz`, `updateTz`, `submitTz`)
- Секции ТЗ (заголовок, редактируемый текст), список открытых вопросов с полями ответа, версия и происхождение (`AI` или `STAFF`), комментарий проверяющего, если был (`lastReviewComment`, выделен).
- Кнопка «Сохранить» (`updateTz` с `baseVersion`). При `409 STALE_VERSION` предложение перезагрузить. Отредактированные секции помечены.
- Кнопка «Отправить на проверку» (`submitTz` с текущей `version`), доступна в `DRAFT_READY` и `NEEDS_REWORK`. После отправки редактирование недоступно, состояние `IN_REVIEW`.

**Шаг QUOTES_NMC** (`createQuoteRequest`, `createQuote`, `listQuotes`, `getQuoteComparison`, `updateQuoteData`, `deleteQuote`, `getNmc`, `calculateNmc`, `submitNmc`)
- Блок «Запрос КП»: выбор подрядчиков из `GET /dev/contractors`, кнопка «Подготовить письмо» (`createQuoteRequest`). Показывается тема, текст, вложения письма. Надпись «Письмо не отправляется (демо)».
- Блок «Полученные КП»: кнопка «Добавить КП» (выбор подрядчика необязателен и файлов, регистрируются через `dev/files`, вызов `createQuote`). Список КП с состоянием извлечения (`EXTRACTING`, `EXTRACTED`, `AI_FAILED`), подрядчик, итог, срок, гарантия. Правка данных КП (`updateQuoteData` с `baseVersion`), удаление (`deleteQuote`).
- Блок «Сравнение» (`getQuoteComparison`): таблица позиций по КП, расхождения и флаги `MISSING`, `MISMATCH`, `OUTLIER` явно подсвечены с пояснением.
- Блок «НМЦ»: кнопка «Рассчитать» (`calculateNmc`), результат (метод, сумма, обоснование, версия, комментарий проверяющего), кнопка «Отправить на проверку» (`submitNmc`).

**Шаг TENDER** (`getTender`, `selectWinner`)
- Документы конкурса (названия, кнопка скачивания, см. «Скачивание файлов» выше).
- Предложение победителя от ИИ: КП, обоснование, баллы по критериям.
- Выбор победителя из КП (по умолчанию предложенный) и комментарий, кнопка «Выбрать» (`selectWinner`). После выбора показывается тип договора (`STANDARD` или `NON_STANDARD`), документ договора и замечания юриста (`lawyerNotes`) для нестандартного.

**Шаг PACKAGE** (`getPackage`, `submitPackage`)
- Четыре документа пакета с кнопками скачивания, версия, комментарий проверяющего.
- Кнопка «Отправить на проверку» (`submitPackage` с версией). После утверждения показывается «Пакет утверждён» и дата (`approvedAt`), заявка `COMPLETED`.

Общие правила: кнопка действия видна только в тех состояниях шага, где `docs/API.md` разрешает действие; недоступные действия скрыты или отключены с подсказкой причины.

## `/approvals` (REVIEWER)

Вызов: `listApprovals`. Таблица или карточки: тип (ТЗ, НМЦ, пакет), адрес, срочность, кто и когда отправил, состояние. Фильтр по состоянию (`PENDING` по умолчанию). Срочные выше.

## `/approvals/[id]` (REVIEWER)

Вызов: `getApproval`. Показывает объект проверки (текст ТЗ, или расчёт НМЦ с КП, или документы пакета с договором и замечаниями юриста, всё только для чтения), версию, кто отправил.

- «Утвердить» (`approve` с `subjectVersion`, комментарий необязателен).
- «Вернуть на доработку» (`reject` с `subjectVersion`, комментарий **обязателен**, без него кнопка неактивна).
- Устаревшая версия (`409 STALE_VERSION`) показывает предложение обновить.
- Уже принятое решение: только просмотр, кто и когда решил.

## `/journal` (REVIEWER)

Вызов: `listApprovalJournal`. Таблица: время, заявка, тип, версия, решение, кто решил, комментарий. Только чтение.

## `/dev` (все роли)

Служебный экран, в навигации в виде небольшой ссылки «Демо-панель».

- Журнал событий (`GET /dev/events`), обновление раз в 2 секунды: тема (`ai.jobs`, `ai.results`, `notifications`), тип, заявка, текст. Именно здесь видно «уведомления» и работу «ИИ».
- Кнопка «Сбросить демо» (`POST /dev/reset`) с подтверждением, после неё переход на `/login`.
