# SPEC: демо-прототип YKit на Nuxt

## 1. Цель

Показать задумку YKit одним запуском: как заявка жителя проходит по шагам закупки, где работает ИИ, где решает человек. Прототип не доказывает ничего про качество ИИ, нагрузку или безопасность.

Что должно быть видно (пять идей):

1. **Заявка запускает автоматическую обработку.** Подача заявки создаёт задание ИИ, результат приходит позже и лежит как **черновик**.
2. **Человек решает на каждом ключевом шаге.** ТЗ, расчёт НМЦ и пакет документов утверждает проверяющий, ИИ ничего не утверждает.
3. **Шаги закупки это автомат состояний** (`StepState`). Недопустимое действие даёт `409 STEP_NOT_ALLOWED`.
4. **Данные принадлежат организации.** `org_id` из сессии ограничивает каждый запрос.
5. **Границы будущих сервисов видны.** ИИ, Documents, Reference Data и Notifications спрятаны за интерфейсами, события пишутся в журнал, как будущий outbox.

## 2. Не цели

Реальный OIDC и JWT, реальный ИИ, реальные файлы и генерация документов, реальные уведомления и web push, PostgreSQL, брокер, производительность, масштабирование, безопасность вне `127.0.0.1`, миграции базы, PWA, несколько УК с отдельным администрированием, интернационализация, тёмная тема.

## 3. Архитектура

Один процесс Nuxt (интерфейс Vue и сервер Nitro), один файл SQLite.

```
Браузер (страницы Nuxt)
   │  $fetch /api/v1/..., Authorization: Bearer <демо-токен>
   ▼
server/api/v1/*  (контракт OpenAPI, проверка токена и роли)
   │
   ├─ server/modules: requests, workflow, approvals, quotes    бизнес-логика без HTTP
   │        │
   │        └── server/gateway: AiGateway, DocumentsGateway, ReferenceGateway, NotificationsGateway
   │                         │ мок-реализации (server/mock)
   ▼                         ▼
SQLite (data/demo.db)        фикстуры (server/mock/*.json)

server/plugins: обработчик ai_jobs (каждые 200 мс)
```

Интерфейс получает данные только через `/api/v1`. Прямого доступа страниц к SQLite нет, чтобы границу «интерфейс ↔ Core» было видно и её можно было потом заменить настоящим Core.

### Что настоящее, что мок

| Часть | В прототипе |
|---|---|
| Заявки, шаги, автомат состояний | Настоящие |
| Согласования и журнал (только добавление) | Настоящие |
| Версии ТЗ и НМЦ, проверка устаревшей версии | Настоящие |
| Сравнение КП (расхождения, выбросы) | Настоящая логика на мок-данных |
| Расчёт НМЦ | Настоящая арифметика, метод условный |
| Изоляция по `org_id` | Настоящая |
| Вход и токены | Мок: принимается любой вход, токен непрозрачный |
| ИИ | Мок: фикстуры по правилам |
| Documents | Мок: метаданные в таблице, скачивание отдаёт текст-заглушку |
| Reference Data | Мок: три вымышленные организации |
| Notifications | Мок: запись в журнал событий |
| Брокер | Нет: `event_log` и `ai_jobs` |

## 4. Принятые решения

| № | Решение | Причина |
|---|---|---|
| 1 | Nuxt (актуальная стабильная версия, проверить в фазе 0), TypeScript | Задано пользователем |
| 2 | SQLite через `better-sqlite3` (синхронный драйвер, собирается под Node) | Простейший вариант для Nitro. Если драйвер не собирается на установленном Node, взять встроенный `node:sqlite` и записать в `docs/DECISIONS.md` |
| 3 | Без ORM, SQL пишется руками | Схема маленькая, ORM только добавит риска |
| 4 | Мок ИИ асинхронный: задание в `ai_jobs`, обработчик по таймеру | Видны `PROCESSING` и `DRAFT_READY`, как в настоящем сервисе |
| 5 | Задержка мока ИИ `DEMO_AI_DELAY_MS`, по умолчанию 1500, `0` без ожидания | Живая демонстрация и быстрые тесты |
| 6 | Организация одна по умолчанию (`demo-org`), вход принимает любой `orgId` | Показать изоляцию без отдельной регистрации |
| 7 | Роль задаётся при входе или определяется по имени (`docs/MOCKS.md`, п. 1) | Любой вход принимается, но демонстрация ролей управляемая |
| 8 | Токен непрозрачный, таблица `sessions`, на клиенте хранится в cookie `demo_token` (`useCookie`) | Не изображаем JWT |
| 9 | Файлы не хранятся: принимается любой UUID. Кнопка «Прикрепить фото» вызывает `POST /dev/files` с именем выбранного файла, содержимое не читается и не отправляется | Documents это мок |
| 10 | Журнал согласований защищён триггерами SQLite | Показать задумку неизменяемого журнала |
| 11 | Готовность ИИ интерфейс узнаёт опросом `GET` раз в секунду, пока шаг в `PROCESSING` | Открытый вопрос контракта решён самым простым способом |
| 12 | Клиент не ходит в интернет, шрифты и иконки локальные | Прототип должен работать без сети |
| 13 | Сервер на `127.0.0.1`, баннер «Демо» | Принимается любой вход |

## 5. Открытые вопросы: значения в прототипе

| Вопрос | Значение |
|---|---|
| Когда заявка `COMPLETED` | После утверждения пакета |
| Откуда адрес жителя | Из сессии (`address` при входе, по умолчанию условный) |
| Значения `triage.route` | `EMERGENCY_CONTRACTOR_CALL` и `PLANNED_PROCUREMENT` |
| Метод НМЦ | `average_of_quotes` |
| Формат документов | Нет файлов, только `DocumentRef` и текст-заглушка при скачивании |
| Канал отправки запроса КП | Не отправляется, показывается только текст письма |

## 6. Критерии приёмки

См. «Определение готовности» в `PROMPT.md`. Дополнительно:

- [ ] После `POST /api/v1/dev/reset` база возвращается к исходному состоянию.
- [ ] Любое действие, меняющее данные, оставляет запись в `event_log` или `approval_journal`.
- [ ] Ни один мок-текст не содержит реальных нормативных ссылок, цен и организаций.
- [ ] Во вкладке Network браузера нет запросов на внешние адреса.
